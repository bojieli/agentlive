# Artifact bundles

Use `--artifact-bundles` with native `import` or `publish` to capture supported HTML artifacts and their dependencies as one attachment. The option also flows through managed launch and family capture. Local file HTML, inline HTML and authenticated remote HTML use the same bundle builder. Native adapters still determine which source objects they expose as artifacts; enabling bundles does not add unsupported native source-object conversion.

For example:

```sh
agentlive import --agent opencode --source ./export.json \
  --artifact-bundles --artifact-root ./artifacts --artifact-base ./artifacts
```

Remote dependencies require the explicit `--remote-artifact-policy` described in [remote artifact capture](remote-artifacts.md). Inline HTML resolves relative dependencies against `--artifact-base` (or the source directory by default for imports); the allowed roots still apply. OpenCode live capture requires explicit local artifact roots.

The publisher saves the filtered bundle and a request-bound outcome before upload. Retry reuses that bundle without rereading its dependencies. A changed native descriptor/source identity creates a new immutable version; an unchanged URL is not polled for updated content. Bundle mode participates in capture-policy fingerprints, so keep `--artifact-bundles` consistent across retry/live continuation. Adding or removing it on an existing binding requires migration, which remains unimplemented.

Bundles have `live-capture` provenance because the dependency graph is captured now; a historical root alone does not prove historical dependency contents. A crash before the outcome checkpoint may require recapture, and the existing spool rejects changed bytes for the same source identity. Keep the configured artifact root directories present when reattaching, even if their files are gone.

The library APIs remain `captureArtifactBundle`, `createBundleLoader`, and the browser-compatible `decodeArtifactBundle`. The browser attachment inspector now verifies the bundle manifest and all leaves, lists captured files, exposes per-file downloads and escaped source, and reports unavailable references. Selecting HTML shows a static preview; PNG, JPEG and static WebP files use bounded image previews. Captured `<picture>` sources and `srcset` candidates render with their media queries, width/density descriptors and `sizes` values. Only verified, bounded PNG, JPEG or static WebP candidates are included, with a limit of 512 candidates per preview; unavailable or malformed candidates receive a notice. Static HTML renders supported markup, captured stylesheets (including supported imports) and bounded captured PNG, JPEG and static WebP images. Scripts, embedded documents, forms and external navigation are disabled. Unsupported media and styles receive a preview notice while the original verified bytes remain downloadable.

Static preview uses a trusted `/artifact-preview` wrapper with a dedicated CSP, an opaque sandbox origin, and an inner sandboxed document with scripts and network access disabled. The wrapper receives only generated preview markup, never viewer credentials. The main application CSP allows same-origin frames but retains its script/style restrictions. Static preview bounds HTML source to 1 MiB, nodes to 20,000, nesting to 128, expanded styles to 2 MiB, raster bytes to 8 MiB and output markup to 12 MiB. These are input bounds, not measured long-session rendering guarantees. An explicit Run interactive preview action is available for the supported script subset described below; static previews remain the default.

A bundle is one attachment with media type `application/vnd.agentlive.artifact-bundle+json`. Its JSON envelope contains a versioned manifest, the SHA-256 hash of the canonical manifest, and base64 blobs addressed by SHA-256. The manifest maps safe bundle-relative paths to media types, byte counts and hashes. Hashes cover filtered, rewritten file bytes. Internal links use paths rather than content hashes, allowing cyclic dependencies without circular hash calculation.

The capture library assigns generated filenames, resolves links against their original source URL, and rewrites a broadcast copy. HTML `src`, `href`, `poster`, `data`, action attributes and inline styles are processed with an HTML parser. Stylesheets and inline CSS use CSS/value parsers for `url(...)` and `@import`. Responsive `srcset`/`imagesrcset` candidates preserve their width/density descriptors. The first source `<base href>` controls dependency resolution; source base href attributes are removed from the rewritten document. JavaScript static imports/reexports and literal dynamic imports are captured recursively, including cyclic modules; inline module scripts use the document base. Rewritten module specifiers use explicit relative paths.

Computed imports, template imports containing substitutions, import maps/bare module names, `import.meta` use, and standalone XML/SVG references currently produce explicit unsupported entries. Arbitrary runtime requests (for example `fetch()` and asset names computed by executing application code) are not evaluated or inferred. Scripts are never executed by capture. Unsupported/out-of-scope/missing/depth-limited references are recorded in the manifest and, where processed, rewritten to missing bundle-relative targets. This is not a claim that every dependency form is supported.

The loader reads only configured filesystem roots and explicitly allowed HTTP(S) origins. Data URLs are decoded through the bounded shared decoder. Local copies check regular-file type, byte limits, metadata stability and path identity; symlinks resolving outside allowed roots are unavailable. Remote files use the existing authenticated capture policy. No original source file is modified. Capture filtering is supplied explicitly by the caller and runs after dependency rewriting.

Limits are 100,000 HTML nodes per document, 256 files, eight dependency edges in depth, 4,096 reference visits, 2,048 unavailable references, 16 MiB total source bytes, 16 MiB total rewritten file bytes and 24 MiB encoded bundle bytes. The decoder verifies manifest and leaf hashes, canonical base64, file sizes, path uniqueness, entrypoint presence and the absence of unreferenced blobs before returning any file. Text is UTF-8; invalid text is rejected.

The current format carries the whole graph in one attachment, so its eventual publication can use the existing durable attachment upload and archive path. CLI imports now have byte-exact recording archive round-trip tests, and live publication has immutable bundle revision coverage. Interactive previews and broader media/CSS fidelity remain unfinished. Static previews read verified dependency bytes from the downloaded bundle; no separate dependency HTTP endpoint is required. No artifact code is executed by the capture library.

The current bundle capture policy is version 2, reflecting the expanded dependency rules. Bindings captured with policy version 1 require explicit migration; the envelope format remains version 1.

Browser evidence: `node scripts/probe-bundle-preview.mjs` uses real Chrome and the production preview wrapper/CSP. It checks rendered text, imported CSS, PNG/JPEG/WebP decoding, responsive picture selection, disabled scripts/forms/navigation, absence of external/service requests, missing-reference UI, exact per-file download and mobile viewport selection. Reports and screenshots are written to `probe-results/bundle-preview/`. The harness now exercises the production AttachmentViewer dialog and authorized download before BundleViewer renders. It checks close/reopen, Escape, corrupt download rejection and successful retry. Broader lifecycle/fault and physical-device acceptance remain open.

JPEG previews preflight baseline/progressive 8-bit frame dimensions, segment framing, scan count and end markers before browser decoding. Encoded files are capped at 8 MiB, dimensions at 8192 per axis and 16 megapixels total; unsupported frame modes and dynamic height updates are rejected. This is a marker preflight, not a JPEG entropy decoder. Browser decode failure does not invalidate the original downloadable bytes.

Static WebP previews verify RIFF size/chunk bounds, VP8 or VP8L dimensions and optional VP8X canvas agreement under the same 8 MiB/8192-axis/16-megapixel raster limits. Animated WebP is download-only. Container preflight does not replace browser pixel decoding.

Ordinary `text/html` attachments now use the same static renderer after their attachment hash is verified, even without bundle capture. Inline styles and supported markup render; separate images/stylesheets are not fetched and generate missing-dependency notices. Files exceeding preview limits retain their verified original download. This preview does not turn a single file into a published bundle or claim its dependencies were captured.


## Explicit interactive HTML previews

The attachment inspector offers **Run interactive preview** for verified HTML attachments and selected HTML bundle files. Scripts execute only after that action. **Stop interactive preview** removes the executing frame; running it again starts from captured state. Closing the inspector or changing the selected bundle file also removes the interactive frame.

The supported subset includes classic inline scripts, captured external JavaScript, captured module graphs, event handlers, canvas and basic form controls. External classic scripts use captured bytes as data URLs, preserving defer/async attributes. Form submission, embedded documents, network resource loads and frame navigation are restricted by sandbox and CSP. CSS and raster dependencies use the same captured-resource compiler as static previews. Missing scripts, source import maps and unsupported module syntax produce an explicit unsupported message with static preview and verified download still available. Script text is bounded to 2 MiB in total, in addition to the existing HTML/output limits. Broader module syntax and HTML/media compatibility remain required feature work.

The trusted `/artifact-interactive` wrapper and its child use opaque sandbox origins with script permission but no same-origin permission. The wrapper accepts markup only from its parent at the application origin and passes no viewer credentials. Its inherited policy blocks network connections, fetched scripts, frame navigation and form submission; generated document policy further restricts resources. The application page's script policy is unchanged. A blocked self-navigation can leave an error document in the artifact frame; Stop and Run recreate it.

The Chrome probe covers an interactive counter, a captured external deferred script, standalone HTML execution mode, parent-document isolation, blocked fetches and external/service self-navigation, stopping and rerunning. It records no external or service requests from the test artifact. This is local Chrome evidence for that subset, not full browser/device/resource-exhaustion or security acceptance. The full production gate remains open.


### Captured JavaScript modules

Interactive previews execute captured static imports, re-exports and literal dynamic imports, including cyclic graphs, external entry modules and inline module scripts. The compiler rewrites captured relative specifiers to stable generated names and emits an import map mapping those names to captured data URLs. Assigning names before following dependencies preserves cycles; script bytes are counted once per module file. The map precedes all artifact scripts. No source URL or service credential is required for module loading.

The browser compiler uses the JavaScript build of es-module-lexer, which requires neither dynamic evaluation nor WebAssembly CSP permission. Graph compilation is capped at 256 modules, depth 128, 4096 import references and the shared 2 MiB script-source budget. Existing document/output bounds still apply.

Computed/template imports, import.meta, source import maps/bare specifiers, import attributes, type-only imports and nonstandard import phases are explicitly unsupported. Those cases keep the static preview/download available. Arbitrary runtime loads and artifact backends are not resolved. Module-specific compatibility and wider browser/resource-exhaustion acceptance remain open. The real Chrome probe executes a cyclic graph, re-export, literal dynamic import and inline entry module while retaining its isolation/no-network checks.
